# Участие в разработке

Проект использует [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/) для автоматического управления версиями и генерации CHANGELOG через [release-please](https://github.com/googleapis/release-please).

## Формат заголовка коммита и PR

```
<тип>(<область>): <описание>
```

Примеры:
```
feat: добавить поддержку нового типа устройства
fix: исправить краш при загрузке конфига
chore: обновить зависимости
docs: обновить README
refactor: вынести логику парсинга в отдельный модуль
```

## Допустимые типы

| Тип        | Что делает с версией | Когда использовать                          |
|------------|----------------------|---------------------------------------------|
| `feat`     | minor (1.x.0)        | Новая функциональность                      |
| `fix`      | patch (1.0.x)        | Исправление бага                            |
| `chore`    | —                    | Обслуживание, обновление зависимостей       |
| `docs`     | —                    | Изменения в документации                    |
| `refactor` | —                    | Рефакторинг без изменения поведения         |
| `test`     | —                    | Добавление или исправление тестов           |
| `ci`       | —                    | Изменения в CI/CD                           |
| `perf`     | patch (1.0.x)        | Улучшение производительности                |

Для **breaking change** добавь `!` после типа или `BREAKING CHANGE:` в тело коммита — это поднимет major-версию (x.0.0):
```
feat!: переработать API конфигурации устройства
```

## Как работает автоматический релиз

1. После merge в `master` release-please анализирует коммиты и создаёт PR с обновлённым `CHANGELOG.md` и версией в `wasm/package.json`
2. PR вливается автоматически
3. Создаётся GitHub Release с тегом версии

> PR с заголовком не по конвенции не пройдёт проверку CI и не будет влит в `master`.
