# Мемо-кэш шины DALI: дизайн и причина отзыва (SOFT-7409)

Статус: **отозвано из редактора 2026-08-31**, возврат — только вместе с
индикацией происхождения данных в UI. Трекинг: SOFT-7409. Код мемо остаётся
upstream (wb-mqtt-dali#227, `wb/mqtt_dali/memory_cache.py` +
`WBDALIDriver._send_through_memory`), выключен по умолчанию (`memory=None`);
обвязка редактора снята коммитом «chore(dali): withdraw the memory memo» на
`feat/dali-pyodide`. ADR 4–6 в `dali-wasm-arc42.ru.md` помечены отозванными.

## 1. Задача, которую решал мемо

Каждый обмен по DALI через WB-DALI стоит ~46 мс (кадр туда-обратно на
1200 бод + Modbus). Открытие страницы устройства и инициализация начинаются
с одних и тех же чтений: банк памяти 0 (GTIN, серийник, версии), банк 1
(OEM), затем «настроечная» развёртка — 16 сцен, группы, уровни, у DALI-2 ещё
схемы событий и таймеры. Итого 50+ кадров на устройство с ответами, которые
сами по себе не меняются.

На контроллере демон живёт долго и платит один раз. В браузере демон живёт
ровно столько, сколько вкладка, — каждый визит был холодным стартом.
Замерено с мемо: **−54 % кадров** на открытие устройства (ADR 4),
**−30 кадров** на страницу настроек (ADR 5).

## 2. Как мемо устроен (реализовано в wb-mqtt-dali#227)

- **Схема кэша — сам протокол IEC 62386**, не объектная модель демона: ключи
  вида «банк/смещение устройства N», «QuerySceneLevel(3) gear 7». Демон может
  рефакториться — мемо не заметит; незнакомый запрос = промах = шина.
- **DTR-тень**: `ReadMemoryLocation` не называет цель — банк/смещение живут в
  общих регистрах DTR0/DTR1 с автоинкрементом. Мемо ведёт тень регистров,
  DTR-записи всегда уходят на провод, батч обслуживается только целиком
  (один промах — весь батч в шину; никогда смесь памяти и провода).
- **Модель доверия**: восстановленная запись ключуется 24-битным случайным
  адресом и используется после того, как устройство на этом коротком адресе
  подтвердит его на проводе — 3 кадра против ~50 заменяемых.
- **Инвалидация**: INITIALISE/RANDOMISE/PROGRAM SHORT ADDRESS сбрасывают мемо
  шины; любая send-twice-запись забывает настройки цели; неответ становится
  фактом «не реализовано» только после 3 подряд.
- **Явные исключения**: живое состояние (actual level, статусы, входы),
  QueryContentDTR0/1 (это верификации), всё под device type (ответ DT8
  размазан между обратным кадром и DTR0 устройства), QueryNextDeviceType
  (последовательность, не значение).

## 3. Почему отозван

**Кэшированные значения показывались неотличимо от свежепрочитанных.**
Инвалидация мемо видит только записи, прошедшие через наш демон: второй
мастер или ручной DALI-программатор на той же шине перепишет сцены/группы —
мемо отдаёт устаревшие байты неограниченно долго. Проверка случайного адреса
доказывает «то же устройство», но не «те же настройки». Для identity-банков
(GTIN/серийник) риска нет — но и там честность требует пометки.

## 4. Дизайн возврата (проработан, отложен)

1. **`memory_cache.py`**: штамп `learned_at` на запись `(kind, short)` —
   ставится при первом обучении, переносится через `snapshot()`/restore,
   повторными обучениями не «освежается» (консервативная честность: дата в
   баннере не моложе реального возраста данных). `served_at` — в
   `apply_served()`, т.е. только когда батч реально обслужен из мемо.
2. **Рантайм браузера** (демон не трогаем): хост владеет объектами
   `MemoryCache` — статус на устройство (`restored`, `learned_at`,
   `confirmed_at`, `served`) наружу через существующий `browser.py` API.
3. **Страница homeui**: баннер уровня страницы — пер-контрольные бейджи
   невозможны без правки демона, происхождение не протащить через
   немодифицированные MQTT-контролы. Текст: «Настройки и identity
   восстановлены из кэша от ⟨дата⟩; устройство подтвердило identity в
   ⟨время⟩. Живые значения (уровни, статусы, входы) всегда читаются с шины».
   Кнопка «Перечитать с шины» = `invalidate` ключа + повторное чтение
   страницы. Дата — `learned_at` **старейшей** обслуженной записи, не время
   файла снапшота. Баннер не должен переобещать: живые значения из мемо не
   отдаются никогда.
4. **Контроллер**: мемо не браузерная особенность — с `data_dir()` из #228
   его можно включить и на контроллере (то же −54 % на открытие страниц).
   Отдельное решение, отдельный риск-анализ.

## 5. Рассмотренная альтернатива: персистентность состояния демона

Снапшот объектов `DaliDevice` и пр., верифицируемый тем же случайным
адресом. Жизнеспособна; отклонена по двум причинам (обе — стоимость
сопровождения, не корректность):

- схема снапшота = внутренняя объектная модель демона: каждый рефакторинг
  классов устройств становится миграцией формата, навсегда; у мемо схема —
  международный стандарт, который не движется;
- страница при открытии всё равно спрашивает демон, а демон идёт в шину —
  значит и там нужен перехват «ответить из состояния или идти в провод» в
  пути запросов, т.е. та же логика serve-or-forward, но ключованная по
  объектам, с более грубым фолбэком (устройство целиком, а не кадр).

Если у демона появится собственный стабильный API экспорта состояния —
альтернативу пересмотреть (см. ADR 4).
