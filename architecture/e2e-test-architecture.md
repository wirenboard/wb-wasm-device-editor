# Архитектура E2E-тестов — Wiren Board WASM Device Editor

_По методологии arc42_

---

## 1. Введение и цели

### 1.1 Обзор требований

Wiren Board WASM Device Editor — браузерное приложение для конфигурации
устройств Modbus RTU. Приложение полностью работает в браузере: стек протокола
Modbus скомпилирован из C++ в WebAssembly, а связь с устройствами осуществляется
через WebSerial API (только Chrome).

E2E-тесты должны проверять полный пользовательский сценарий — от открытия
приложения, выбора серийного порта, сканирования устройств, просмотра/редактирования
параметров и сохранения конфигурации — **без реального оборудования и
скомпилированного WASM-бинарника**.

### 1.2 Цели качества

| Приоритет | Цель | Метрика |
|-----------|------|---------|
| 1 | **Детерминированность** | Ноль нестабильных падений на 100 последовательных запусках |
| 2 | **Быстрая обратная связь** | Полный набор тестов выполняется менее чем за 30 секунд |
| 3 | **Реалистичные данные** | Ответы моков используют реальные шаблоны устройств из wb-mqtt-serial |
| 4 | **Поддерживаемость** | Добавление нового типа устройства требует лишь одного вызова `loadTemplate()` |
| 5 | **Готовность к CI** | Запускается headless без внешних зависимостей, кроме npm |

### 1.3 Заинтересованные стороны

| Роль | Интерес |
|------|---------|
| Разработчик редактора устройств | Обнаружение UI-регрессий до мержа |
| CI-пайплайн | Блокировка PR при падении автоматических тестов |
| QA-инженер | Расширение тестов для покрытия новых типов устройств и сценариев |

## 2. Ограничения

### 2.1 Технические ограничения

| Ограничение | Обоснование |
|-------------|-------------|
| **WASM-бинарник отсутствует в репозитории** | `module.js` генерируется Emscripten (`emmake`). Бинарник ~5 МБ, требует тулчейн кросс-компиляции C++ и добавлен в gitignore (`wasm/public/module.*`). Тесты должны работать без него. |
| **WebSerial работает только в Chrome** | `navigator.serial` недоступен в Firefox или WebKit. Тесты запускаются только в Chromium. |
| **Нет реальных устройств** | У CI-раннеров нет USB-серийного оборудования. Весь стек серийной коммуникации должен быть замокан. |

### 2.2 Организационные ограничения

| Ограничение | Обоснование |
|-------------|-------------|
| **Сосуществование с тестами SW** | PR #21 (вмержен) добавил E2E-тесты service worker в `wasm/e2e/sw-*.spec.ts`, использующие Express-сервер с продакшен-сборкой. Наши тесты должны разделять директорию `wasm/e2e/` и `playwright.config.ts` без конфликтов. |
| **Один воркер** | `workers: 1` — тесты используют общий Vite dev server и состояние serial; параллельное выполнение вызвало бы гонки. |

## 3. Контекст и границы

### 3.1 Контекст системы и граница тестирования

Диаграмма ниже показывает архитектуру приложения в продакшене.
Пунктирная линия `- - -` обозначает границу мокирования: всё **выше** неё
работает в тестах без изменений, всё **ниже** заменено моками.

```
┌─────────────────────────────────────────────────────┐
│                    Браузер                          │
│                                                     │
│  ┌─────────────┐    ┌──────────┐                    │
│  │ React UI    │◄──►│ Module   │    Работает        │
│  │ (MobX)      │    │ (JS-клей)│    как есть        │
│  └─────────────┘    └────┬─────┘                    │
│ - - - - - - - - - - - - -│- - - - граница моков - - │
│                    ┌─────▼─────┐    ┌────────────┐  │
│                    │ SerialPort│◄──►│ WASM C++   │  │
│                    │ (обёртка  │    │ (Modbus)   │  │
│                    │ WebSerial)│    └────────────┘  │
│                    └─────┬─────┘    Заменено        │
│                          │          моками          │
└──────────────────────────┼──────────────────────────┘
                           │ USB
                    ┌──────▼──────┐
                    │ Modbus RTU  │
                    │ устройство  │
                    └─────────────┘
```

| Слой | В продакшене | В тестах |
|------|-------------|----------|
| React UI, MobX-сторы, `script.js`, `serial.js` | Реальный код | **Без изменений** |
| `module.js` (WASM-бинарник) | Скомпилированный Emscripten C++ | `module-mock.ts` — JS-функции, возвращающие данные из реальных шаблонов |
| `navigator.serial` | Chrome WebSerial API | `webserial-mock.ts` — мок порта в памяти |
| Modbus RTU устройство | Реальное оборудование через USB | Отсутствует |


## 4. Стратегия решения

### 4.1 Двухуровневая архитектура моков

**Решение**: Мокать на двух самых нижних уровнях, а не на уровне сторов или HTTP API.

**Обоснование**: У приложения нет HTTP API-слоя — вся коммуникация идёт через
`Module.request() → WASM C++ → SerialPort → navigator.serial`. Мокирование на
границе WASM-функций позволяет всему JavaScript-клею (`script.js`, `serial.js`)
работать по-настоящему, обнаруживая интеграционные баги, которые моки более высокого
уровня пропустили бы.

**Рассмотренная альтернатива**: Прямое мокирование MobX-сторов. Отклонено, так как
это обходит асинхронный паттерн `request/parseReply` в `script.js`, который является
частым источником багов.

### 4.2 Реальные шаблоны вместо рукописных данных

**Решение**: Читать шаблоны устройств из `submodule/wb-mqtt-serial/templates/`
во время запуска тестов и конвертировать их в форматы ответов, ожидаемые фронтендом.

**Обоснование**:
- Шаблоны эволюционируют с выходом новых прошивок. Рукописные схемы рассинхронизируются.
- C++-генератор confed-схем конвертирует `parameters` из словаря
  (`{"baud_rate": {...}}`) в массив (`[{id: "baud_rate", ...}]`). Репликация
  этой конвертации в `load-template.ts` гарантирует соответствие мока реальному пайплайну.
- Добавление нового типа устройства в тесты требует только
  `loadTemplate('config-new-device.json')` — без ручного создания схем.

### 4.3 Инъекция через `context.addInitScript`

**Решение**: Использовать `context.addInitScript()` Playwright для инъекции
обоих моков до выполнения любых скриптов страницы.

**Обоснование**: Vite dev server вставляет `serial.js`, `script.js` и `module.js`
как теги `<script async>`. Порядок загрузки недетерминирован. `addInitScript`
гарантирует запуск кода моков до любого скрипта страницы, независимо от порядка загрузки.

**Рассмотренная альтернатива**: `page.route('**/module.js', ...)` для перехвата
сетевого запроса. Это был первоначальный подход, но он вызывал ~10% нестабильных
падений из-за гонки между перехватом маршрута и механизмом HMR-перезагрузки Vite.
Подход с `addInitScript` и повтором по таймауту снизил нестабильность до 0%.

### 4.4 Плейсхолдер `module.js`

**Решение**: Закоммитить пустой `wasm/public/module.js` через `git add -f`
(обходя паттерн `.gitignore` `wasm/public/module.*`).

**Обоснование**: Без этого файла Vite возвращает 404 для `module.js`, вызывая
ошибку загрузки скрипта, которая не позволяет циклу `waitFor` в init-скрипте
найти `window.Module`. Плейсхолдер содержит одну строку-комментарий. При продакшен-сборке
Emscripten (`emmake`) перезаписывает его реальным WASM-клеем.

`.gitignore` обновлён: вместо `wasm/public/module.*` перечислены конкретные
артефакты сборки (`module.wasm`, `module.data`, `module.worker.js`).
`module.js` больше не игнорируется и отслеживается git нормально.

### 4.5 Разделение проектов Playwright

**Решение**: Использовать фичу `projects` Playwright для разделения тестов моков и
тестов service worker в одном конфигурационном файле.

**Обоснование**: PR #21 добавил SW-тесты (`sw-*.spec.ts`), работающие с продакшен-
сборкой через Express-сервер на порту 3210. Наши тесты моков работают с Vite dev
server на порту 5173. Проекты Playwright позволяют им сосуществовать:

```
projects:
  mock-tests  → testDir: ./tests, baseURL: localhost:5173
  sw-tests    → testDir: .,       testMatch: sw-*.spec.ts
```

**Почему SW-тесты не могут использовать Vite dev server:**

Service worker тесты проверяют офлайн-режим, обнаружение обновлений и
поведение при медленной сети. Это требует возможностей, несовместимых
с Vite dev server:

1. **Продакшен-сборка** — Service worker (`sw.js`) регистрируется и кеширует
   статические ассеты. Vite dev server не отдаёт собранные файлы, инъектирует
   HMR-клиент и не обслуживает `sw.js` так, как это делает реальный деплой.
2. **Остановка/запуск сервера** — Тест офлайн-режима (`sw-offline.spec.ts`)
   вызывает `server.stop()` посреди теста, чтобы симулировать реальный обрыв
   сети, а затем `server.start()` для восстановления. Playwright `webServer`
   нельзя останавливать и запускать изнутри теста.
3. **Модификация `sw.js` на диске** — Тест обновлений (`sw-update.spec.ts`)
   вызывает `mutateSWVersion()`, изменяя `CACHE_VERSION` в файле `sw.js`.
   Браузер при следующем `reg.update()` обнаруживает байтовое отличие и
   активирует новый SW. С Vite dev server файл `sw.js` не отдаётся напрямую
   с диска.

Поэтому SW-тесты управляют собственным Express-сервером (`TestServer`),
обслуживающим `dist-configurator/` (результат `vite build`).

### 5.3 Уровень 3 — Внутреннее устройство мока Module

Мок модуля устанавливает 5 функций на `window.Module`:

| Функция | Триггер | Ответ |
|---------|---------|-------|
| `configGetDeviceTypes(json)` | Запуск приложения | Реальные группы типов устройств из шаблона |
| `configGetSchema(json)` | Выбор типа устройства | Реальная JSON-схема с параметрами, группами, каналами, переводами |
| `portScan(json)` | Нажатие «Сканировать» | Устройства, соответствующие `{baud_rate, parity}` из заготовленных результатов; пусто при `mode:'next'` |
| `deviceLoadConfig(json)` | После выбора устройства | Значения параметров по умолчанию из шаблона; учитывает `window.__mockError` |
| `deviceSet(json)` | Нажатие «Сохранить» | `{success: true}`; сохраняет payload в `window.__lastDeviceSetPayload` |

Все функции используют `setTimeout(() => Module.parseReply(reply), 1)` для
соответствия асинхронному паттерну `request/parseReply` в `script.js`.

### 6.2 Сценарий: Повторная попытка фикстуры при HMR Vite

При первом запуске Vite dev server иногда выполняет «полную перезагрузку»
через HMR (Hot Module Replacement). Это происходит, когда Vite обнаруживает
изменения в файлах или завершает первичную оптимизацию зависимостей. При
такой перезагрузке JavaScript-скрипты страницы (`script.js`, `serial.js`)
перезапускаются, но `addInitScript`-моки **не** переинъектируются, потому
что клиентская перезагрузка через HMR не является серверной навигацией
(для Playwright это та же страница). В результате `window.Module` создаётся
заново, но мок-функции не устанавливаются, и `Module.serial` остаётся
`undefined`.

Фикстура обрабатывает этот случай так:

```
  Фикстура                                 Браузер
   │                                           │
   │  goto('/')                                │
   │──────────────────────────────────────────►│
   │                                           │  Vite отдаёт страницу
   │                                           │  HMR вызывает полную
   │                                           │  перезагрузку
   │                                           │  (скрипты перезапускаются,
   │                                           │   но init-скрипты НЕ
   │                                           │   выполняются повторно при
   │                                           │   клиентской перезагрузке)
   │                                           │
   │  waitForFunction(Module.serial)           │
   │  ... 10 секунд ...                        │
   │  ✗ ТАЙМАУТ                                │
   │                                           │
   │  catch → page.reload()                    │
   │──────────────────────────────────────────►│
   │                                           │  Полная серверная
   │                                           │  перезагрузка
   │                                           │  Init-скрипты
   │                                           │  ПЕРЕЗАПУСКАЮТСЯ
   │                                           │  Module.serial есть ✓
   │                                           │
   │  waitForFunction(Module.serial)           │
   │◄──────────────────────────────────────────│  ✓ успех
```

## 8. Сквозные концепции

### 8.1 Асинхронный паттерн `request/parseReply`

`Module.request(method, params)` работает следующим образом:

1. Устанавливает `Module.finished = false`
2. Вызывает WASM-привязанную функцию (например, `Module.portScan(json)`)
3. Запускает цикл опроса через `setTimeout`, проверяя `Module.finished`
4. WASM-функция (или наш мок) вызывает `Module.parseReply(json)`, который
   устанавливает `Module.finished = true` и сохраняет результат в `Module.reply`
5. Цикл опроса разрешает промис с `Module.reply`

Мок-функции **обязаны** использовать `setTimeout(() => M.parseReply(reply), 1)` —
синхронный вызов установил бы `finished = true` до начала цикла опроса, но
функция `request()` читает `finished` синхронно перед запуском цикла, поэтому
технически это тоже работает. Задержка в 1 мс — для надёжности и согласованности
с реальным асинхронным поведением.

### 8.2 Протокол итерации PortScan

`PortScan.exec()` перебирает `8 скоростей × 3 чётности = 24 комбинации`.
Для каждой комбинации:

1. Отправляет `portScan({mode: 'start', baud_rate, parity, data_bits, stop_bits})`
2. Если устройства найдены, повторно отправляет `portScan({mode: 'next', ...})`
   до получения пустого ответа
3. Переходит к следующей комбинации baud/parity

Мок возвращает совпадающие заготовленные устройства при `mode:'start'` и всегда
возвращает пустой массив при `mode:'next'`, симулируя одну страницу результатов
на комбинацию.

### 8.3 Конвертация формата параметров шаблона

Сырые шаблоны в `wb-mqtt-serial` хранят параметры как словарь:

```json
{
  "parameters": {
    "baud_rate": { "title": "Baud rate", "default": 96, "enum": [96, 192, ...] }
  }
}
```

C++-генератор confed-схем конвертирует это в массив для фронтенда:

```json
{
  "parameters": [
    { "id": "baud_rate", "title": "Baud rate", "default": 96, "enum": [96, 192, ...] }
  ]
}
```

`load-template.ts` реплицирует эту конвертацию, чтобы
`DeviceSettingsObjectStore._buildParameters()` получил ожидаемый формат.

### 8.4 Регистровые vs человекочитаемые значения

Некоторые параметры шаблона используют регистровые значения с человекочитаемыми заголовками:

```json
"baud_rate": {
  "enum": [96, 192, 384, 576, 1152],
  "enum_titles": ["9600", "19200", "38400", "57600", "115200"],
  "default": 96
}
```

Значение `96` — то, что записывается в Modbus-регистр 110; UI отображает «9600».
Мок `deviceLoadConfig` возвращает регистровые значения (совпадающие с тем, что
вернуло бы реальное устройство). Фронтендовый компонент `NumberEditor` отображает
их через `enum_titles`.

### 8.5 Точки инспекции для тестов

Моки предоставляют состояние для тестовых утверждений через `window`:

| Глобальная переменная | Назначение |
|-----------------------|------------|
| `window.__serialMock` | Состояние мока WebSerial: `isOpen`, `isSelected`, `lastRequestPortFilters`, `lastOpenOptions`, `pushResponse()`, `getWrittenData()`, `reset()` |
| `window.__lastDeviceSetPayload` | Последний payload запроса `deviceSet` (для проверки, что Save отправляет корректные данные) |
| `window.__mockError` | Установите в `true`, чтобы `deviceLoadConfig` вернул ошибку |
| `window.Module.reply` | Последний RPC-ответ (стандартный механизм приложения) |
| `window.Module.serial` | Экземпляр SerialPort (доказательство успешной инициализации) |

## 9. Архитектурные решения

### ADR-1: Мокирование на границе WASM, а не на уровне сторов

**Статус**: Принято

**Контекст**: У приложения нет HTTP/REST API. Вся серверная логика работает в WASM.
Необходимо решить, на каком уровне перехватывать для тестирования.

**Решение**: Мокировать `Module.configGetDeviceTypes`, `Module.portScan` и т.д. —
5 WASM-привязанных функций. Оставить `script.js`, `serial.js`, React-компоненты и
MobX-сторы работать без изменений.

**Последствия**:
- (+) Тесты проверяют реальный асинхронный поток `request/parseReply`
- (+) Тесты проверяют реальную логику итерации `PortScan`
- (+) Тесты проверяют реальный жизненный цикл класса `SerialPort`
- (+) Обнаружение интеграционных багов между JS-клеем и React UI
- (−) Невозможно тестировать реальное кодирование/декодирование протокола Modbus
- (−) Невозможно тестировать компиляцию WASM или логику C++

### ADR-2: Чтение реальных шаблонов во время тестов

**Статус**: Принято

**Контекст**: Схемы устройств сложные (15+ параметров, 6 групп, 73 канала только
для MAP3ET). Ручное создание тестовых данных подвержено ошибкам и рассинхронизации.

**Решение**: Читать `config-map3et.json` из субмодуля wb-mqtt-serial во время
тестов через `fs.readFileSync`. Конвертировать формат параметров в соответствии
с выводом C++-генератора confed-схем.

**Последствия**:
- (+) Тестовые данные всегда соответствуют реальному шаблону устройства
- (+) Добавление типа устройства — одна строка: `loadTemplate('config-xxx.json')`
- (+) Изменения параметров шаблона подхватываются автоматически
- (−) Тесты требуют инициализации субмодуля wb-mqtt-serial
- (−) `load-template.ts` реплицирует логику конвертации C++, которая может разойтись

### ADR-3: `context.addInitScript` вместо `page.route`

**Статус**: Принято (заменяет начальный подход с `page.route`)

**Контекст**: Первоначальная реализация использовала `page.route('**/module.js', ...)`
для перехвата сетевого запроса и отдачи кода мока. Это вызывало ~10% нестабильных
падений из-за гонки между регистрацией маршрута и асинхронной загрузкой скриптов Vite.

**Решение**: Использовать `context.addInitScript()` для обоих моков. Init-скрипт
опрашивает `window.Module` (определённый `script.js`) и устанавливает мок-функции
при обнаружении. Плейсхолдер `module.js` предотвращает ошибки 404.

**Последствия**:
- (+) 100% стабильность на 100 последовательных запусках
- (+) Моки сохраняются при перезагрузке страницы (уровень контекста)
- (+) Нет гонки с перехватом сети
- (−) Требуется плейсхолдер `module.js` в репозитории (`.gitignore` обновлён для его отслеживания)
- (−) Цикл опроса `waitFor` добавляет ~5 мс задержки

### ADR-4: Повторная попытка фикстуры при HMR Vite

**Статус**: Принято

**Контекст**: HMR Vite изредка вызывает клиентскую перезагрузку страницы при
начальной загрузке. Когда это происходит, скрипты страницы перезапускаются,
но код `addInitScript` не выполняется повторно (он запускается только при
серверных навигациях), оставляя `Module.serial` неопределённым.

**Решение**: Фикстура оборачивает `waitForFunction(Module.serial)` в try/catch.
При таймауте вызывает `page.reload()` (серверная навигация, перезапускает
init-скрипты) и ждёт снова.

**Последствия**:
- (+) Полностью устраняет нестабильности от HMR
- (+) Максимум одна дополнительная перезагрузка (~1 секунда)
- (−) Маскирует потенциальные реальные ошибки инициализации (смягчается вторым таймаутом)

### ADR-5: Разделение проектов Playwright

**Статус**: Принято

**Контекст**: Два набора E2E-тестов с принципиально разными потребностями:
- Mock-тесты проверяют UI-логику через Vite dev server с подменой WASM-модуля.
- SW-тесты проверяют офлайн-режим, обновления и фолбэки service worker.
  Им нужна продакшен-сборка (`dist-configurator/`) и Express-сервер, который
  можно останавливать/запускать посреди теста и чей `sw.js` можно модифицировать
  на диске. Vite dev server для этих целей не подходит (см. раздел 4.5).

**Решение**: Использовать проекты (`projects`) Playwright для разделения:
- `mock-tests`: `testDir: './tests'`, `baseURL: localhost:5173`, Vite dev server
- `sw-tests`: `testDir: '.'`, `testMatch: 'sw-*.spec.ts'`, собственный Express (`TestServer`)

**Последствия**:
- (+) Один `npm run test:e2e` запускает всё
- (+) Можно запустить только тесты моков: `--project mock-tests`
- (+) Нет конфликтов имён файлов между наборами тестов
- (−) Vite dev server стартует и для SW-тестов, хотя они используют свой Express

## 10. Риски и технический долг

| Риск | Влияние | Смягчение |
|------|---------|-----------|
| Изменение формата шаблонов wb-mqtt-serial | Тесты сломаются, если изменится конвертация dict→array | `load-template.ts` — тонкий адаптер; поломка сразу видна |
| Обновление мажорной версии Vite | Тайминг инъекции `addInitScript` может измениться | Механизм повторной попытки фикстуры поглощает вариации тайминга |
| Изменения WebSerial API в Chromium | `webserial-mock.ts` может стать несовместимым | Мок зеркалит использование в `serial.js`, а не полную спецификацию; важны только используемые поверхности |
| Перезапись плейсхолдера `module.js` сборкой | Выход сборки идёт в тот же путь | Плейсхолдер — одна строка-комментарий; Emscripten заменит его реальным клеем при сборке |

## 11. Глоссарий

| Термин | Определение |
|--------|-------------|
| **confed-схема** | Обёртка JSON Schema, генерируемая C++-функцией `GenerateSchemaForConfed()`, содержащая `device` (шаблон), `properties`, `definitions` и `translations` |
| **DeviceTabStore** | MobX-стор, управляющий одной вкладкой устройства: загружает схему, хранит редактируемые параметры |
| **DeviceTypesStore** | MobX-стор, содержащий все доступные типы устройств; предоставляет загрузку схем через `getSchema()` |
| **init-скрипт** | JavaScript, инъектируемый через `context.addInitScript()` Playwright, выполняющийся до любых скриптов страницы |
| **Module** | Глобальный объект `window.Module`, определённый в `script.js`; предоставляет `request()`, `parseReply()`, `isReady` |
| **PortScan** | Класс в `script.js`, перебирающий комбинации baud/parity и вызывающий `Module.portScan()` |
| **SerialPort** | Класс в `serial.js`, оборачивающий `navigator.serial` с методами `open()`, `close()`, `select()`, `read()`, `write()` |
| **Шаблон (template)** | JSON-файл в `wb-mqtt-serial/templates/`, определяющий параметры, каналы, группы и переводы устройства |
| **WASM-привязанная функция** | JavaScript-функция, связанная с C++ через привязки Emscripten (например, `Module.portScan`) |
