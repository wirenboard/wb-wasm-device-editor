# DALI-конфигуратор в браузере — архитектурная документация (arc42)

Документ описывает архитектуру встраивания DALI-конфигуратора Wiren Board в
автономный браузерный редактор устройств (`wb-wasm-device-editor`) и все
принятые проектные решения. Формат — [arc42](https://arc42.org/); раздел 9
содержит каталог решений (ADR). Английское техническое описание протокола
драйвера и адаптации демона — в `dali-in-the-browser.md`; этот документ шире:
он фиксирует и решения по UI, кэшированию, тестированию и сборке.

## 1. Введение и цели

**Задача.** Дать пользователю полный DALI-конфигуратор — тот же, что на
контроллере Wiren Board, — работающий целиком в браузере: страница homeui,
неизменённый демон `wb-mqtt-dali` и реальный модуль WB-DALI, подключённый по
USB-RS485 через WebSerial. Без контроллера, без сервера, при желании — из
одного HTML-файла без сети.

**Ключевые требования к качеству:**

| Приоритет | Требование |
|---|---|
| 1 | Демон и страница homeui используются **без изменений** — исправление в любом из них достаётся обоим окружениям |
| 2 | Корректность на шине: один запрос в полёте, никакой рассинхронизации указателей очереди шлюза |
| 3 | Скорость повторных сеансов: пол минуты холодного старта недопустимы при каждом открытии |
| 4 | Работоспособность офлайн: единый файл ~25 МБ со всем необходимым |
| 5 | Тестируемость без железа: весь стек должен подниматься против симулятора |

**Заинтересованные стороны:** пользователи модулей WB-DALI (наладка без
контроллера), команда homeui (общая страница), команда wb-mqtt-dali (общий
демон), CI.

## 2. Ограничения

- Демон `wb-mqtt-dali` и python-dali вендорятся **без правок** (скрипт
  `fetch-python-sources.sh`); любые адаптации — только снаружи.
- Страница DALI в homeui — общая для контроллера и редактора; всё
  контроллер-специфичное должно продолжать работать на контроллере.
- Один последовательный канал WebSerial; браузерный chooser портов требует
  жеста пользователя.
- Pyodide: CPython в WASM, в web-worker'e; файловая система не переживает
  перезагрузку страницы.
- DALI-шина: ~46 мс на кадр — физический пол скорости; единственный способ
  ускориться — не посылать кадры.
- Правила репозитория homeui (`project-rules.md`): типы в `types.ts`,
  перечисления вместо строковых литералов, тесты рядом с кодом и т.д.

## 3. Контекст и охват

```
Пользователь ── браузер (Chromium) ── WebSerial ── USB-RS485 ── WB-DALI ── DALI-шина
                    │
        ┌───────────┴─────────────┐
        │ wb-wasm-device-editor   │
        │  ├─ Modbus-редактор     │   (C++ WASM, port/Load RPC)
        │  └─ DALI-страница homeui│
        │       └─ Pyodide-worker │
        │            └─ wb-mqtt-dali (неизменённый) + loopback-брокер
        └─────────────────────────┘
```

Внешние системы: `fw-releases.wirenboard.com` (каталог прошивок, для
офлайн-сборки кэшируется), CDN Pyodide (колёса зависимостей, проверяются по
sha256 из lock-файла), `deveditor.wirenboard.com` (публикация и проверка
обновлений).

## 4. Стратегия решения

1. **Подмена по одному шву, а не форк.** Демон конструирует свой драйвер по
   имени — одно присваивание (`application_controller.WBDALIDriver = …`)
   заменяет весь транспорт. Страница homeui берёт MQTT-клиент из одного
   модуля — vite-подмена этого модуля (`redirectHomeuiMqttClient`) направляет
   её в loopback-брокер. Вкладка шлюза (эмулятор Lunatone — WebSocket-сервер,
   невозможный в браузере) подменяется целым модулем на этапе сборки.
2. **Блокирующий протокол вместо эмуляции wb-mqtt-serial**: перемотка
   указателя, пакетная запись слотов, опрос последнего ответа.
3. **Не посылать кадры повторно** — мемоизация ответов шины: отозвана до
   появления индикации происхождения данных в UI (SOFT-7409, см. ADR 4–6 и
   `dali-memory-cache-postponed.ru.md`); реализация сохранена на ветке
   `soft-dali-memory-cache` в wb-mqtt-dali. Сейчас все чтения идут в шину.
4. **Симулятор на уровне регистров Modbus** — продакшен-код кодирования
   кадров, очереди и коммишининга тестируется, а не обходится.
5. **Возможности хоста** (`daliHostCapabilities`) — то немногое, что страница
   должна знать о хосте (syslog), выключается флагом до первого рендера.

## 5. Блочная структура (строительные блоки)

- `wasm/src/` — оболочка редактора (TypeScript/React):
  `dali-wasm.tsx` (жизненный цикл рантайма, port-gate, retry),
  `mqtt-client.ts` (loopback-клиент, идемпотентный re-attach),
  `pyodide-backend.ts`/`dali-worker.ts` (worker и инлайн-вариант для file://),
  `gateways.ts` (память о найденных шлюзах + восстановление из snapshot скана),
  `boot-failure.ts` (двухстрайковая логика сброса установки).
- `wasm/python/runtime/wbdali_browser/` — рантайм под Pyodide:
  `runtime.py` (порядок загрузки демона, watch_config, пейсинг монитора),
  `dali_driver.py` (блокирующий драйвер, кольцо монитора),
  `browser.py` (API для JS, sim-режим), `sim/` (виртуальный WB-DALI).
- `submodule/homeui/frontend/src/pages/settings/configs/dali/` — страница:
  `device-controls/` (закреплённая полоса контролов, слияние уставка↔чтение),
  `bus-monitor/` (кольцо, свёртка повторов ошибок, пустое состояние панели),
  `tab-toolbar/` (тулбар, публикующий свою высоту для sticky-полосы).

## 6. Runtime-виды

**Загрузка:** scan Modbus → запись шлюзов в localStorage → `#dali` →
проверка порта (для sim slave 250 — пропуск) → boot Pyodide-worker →
`browser.start(scenario, config, groups, port_load)` → демон
поднимается против восстановленных конфига/групп → страница читает
дерево по MQTT-RPC; инициализация устройств идёт за страницей, READY
её не ждёт (ADR 27).

**Чтение страницы устройства (второй сеанс):** как и в первый — все чтения
идут в шину (мемо-кэш отозван, см. ADR 4–5).

**События сенсоров:** кольцо монитора опрашивается всегда (см. ADR-7);
кадры LightEvent/OccupancyEvent доходят до демона и публикуются в контролы —
при условии схемы адресации «короткий адрес + номер компонента» (ADR-12).

## 7. Развёртывание

- **Онлайн**: статика на CDN + Service Worker (DALI-рантайм ~13 МБ не
  прекэшируется — кэш при первом обращении из DALI-вида).
- **Офлайн**: один HTML ~25 МБ (gzip+base64-блобы: WASM, Python, каталог
  прошивок; сетевые обращения с фолбэком на встроенное).
- **CI (Jenkins)**: сборка → pytest рантайма (CPython против симулятора) →
  vitest → офлайн-сборка → e2e (playwright, sim-режим) → публикация.

## 8. Сквозные концепции

- **Ошибки шлюза — это ответы, не исключения**: `raw_value` у ошибочных
  ответов «стреляет» RuntimeError; всё чтение идёт через `raw_of()`.
- **i18n**: все строки страницы — через i18next, en+ru, включая множественные
  формы русского («повторено 2 раза»).

## 9. Архитектурные решения (ADR)

| № | Решение | Обоснование | Альтернатива и почему нет |
|---|---|---|---|
| 1 | Блокирующий драйвер: перемотка → пакет слотов 0..n-1 → опрос последнего ответа | Перемотка самосинхронизирует указатель (сбой не накапливается); пакет даёт 46 мс/кадр — физический пол | Счётчик слотов в драйвере: один потерянный кадр парковал очередь до полного оборота (наблюдалось на железе) |
| 2 | Демон без правок: рантайм ходит в него через публичные швы (фабрика драйвера, `RegisterLink`, посев групп, каталог данных, ожидания) | Швы добавлены upstream (wb-mqtt-dali#228) после того, как подмена атрибута модуля и обёртки над методами показали себя хрупкими; вендоринг закреплён за веткой стека до мержа | Подмена `WBDALIDriver` по имени + monkeypatching (исходное); форк wb-mqtt-dali |
| 3 | Loopback-брокер + подмена модуля mqtt-client в homeui | Брокер нужен **не ради RPC**, а ради плоскости состояния и событий: демон публикует каждое устройство, группу и broadcast как retained-топики `/devices/…`, а события DALI-2 и строки монитора приходят с шины спонтанно; homeui читает всё это через `devicesStore` (`/devices/#`). RPC пущен по тому же брокеру ради одного шва вместо двух, а не по необходимости. Что именно ходит — в §9.1 | Паттерн Modbus-редактора — прямая привязка RPC-обработчиков (`wasm_module.cpp` зовёт те же `TRPC*`-классы, что и MQTT-RPC на контроллере, а homeui получает proxy-объект вместо `createRpcProxy`) — для RPC-половины годится и здесь; для плоскости состояния всё равно нужен «брокер по имени» — retained-снимок, подписка, догон. Записано как опция в §11 |
| 4 | **Отозвано (2026-08-31):** мемо банков памяти по случайному адресу | Работало (identity не меняется; проверка — 3 кадра; открытие устройства −54 % кадров), но кэшированные значения показывались неотличимо от свежепрочитанных. Вернуть только вместе с индикацией происхождения в UI — SOFT-7409, дизайн в `dali-memory-cache-postponed.ru.md` | Ключ по конфиговому random: подменённое устройство унаследовало бы чужой identity. Персистентность состояния демона с той же проверкой по случайному адресу: жизнеспособна, но схема снапшота = внутренняя модель демона (миграции навсегда), а перехват «из состояния или в шину» в пути запросов нужен всё равно |
| 5 | **Отозвано (2026-08-31):** мемо настроек (сцены, группы, уровни) с забыванием по send-twice | Инвалидация видит только записи через НАШ демон: второй мастер или программатор на той же шине переписывает настройки — кэш отдаёт устаревшее неограниченно долго, а проверка случайного адреса доказывает «то же устройство», не «те же настройки». −30 кадров на страницу вернутся с SOFT-7409 | Кэшировать всё: живые запросы (actual level) и DT8-цвет исключались явно |
| 6 | Отозвано вместе с мемо: `classify()` — единая классификация команд для трёх обходчиков | Урок остаётся в силе: пропуск вида команды в одном из обходчиков молча рассинхронизировал DTR-тень; код — на ветке `soft-dali-memory-cache` в wb-mqtt-dali | Три независимых разбора (исходное состояние) |
| 7 | Кольцо монитора опрашивается всегда, темп 100 мс/250 мс/1 с | События DALI-2-сенсоров приходят только через кольцо: с выключенным опросом освещённость замерзала. Без DALI-2-устройств на шине — ленивые 1 с | Опрос только при открытом мониторе (исходное, отменено) |
| 8 | Базлайн кольца при инициализации, без публикации | Реальный модуль хранит кадры прошлого сеанса; на контроллере этот снимок приходит retained и отбрасывается — здесь та же семантика | Публиковать всё: «свежие» события из прошлого сеанса при каждой загрузке |
| 9 | Рантайм переживает уход со страницы DALI (`liveBackend`) | Знание демона о шине (163 кадра ре-инициализации лампы, 426 — первая страница) живёт в его памяти | Убивать worker при навигации: всё оплачивается заново |
| 10 | Повторный `attach()` того же бэкенда идемпотентен | Иначе каждое возвращение на страницу добавляло дубль-подписку и кратные доставки | — |
| 11 | Симуляция «на проводе»: sim-режим = шлюз со slave id 250 | e2e поднимает всю страницу (Pyodide+демон+UI) за ~7 с без железа; включается только когда **все** шлюзы симулируемые — реальный модуль нельзя молча увести в симулятор | Отдельный «demo-mode» в UI |
| 12 | Страж схемы адресации событий (баннер + «Установить рекомендуемую схему») | Заводская схема «тип и номер компонента» не содержит адреса отправителя — события декодируются, но не атрибутируются (Illuminance навсегда 0); только схема 2 несёт адрес+номер. Диагностировалось крайне тяжело (SOFT-7398) | Молчаливое авто-исправление демоном (предложено upstream). Атрибуция по «единственному компоненту этого типа и номера на шине» была реализована (wb-mqtt-dali#222) и отклонена как хрупкая — угадывание по текущему составу шины; PR закрыт |
| 13 | Полоса избранных контролов: эвристика по структуре + слияние уставка↔чтение | «Wanted Level (1.8 %)», swatch у Set RGB: пара занимает один слот; чтения сенсора получают «имя: **значение**» — «Освещённость 1 537» перестало читаться как 1537 | Показать всё: у сенсора 20 кнопочных индикаторов топят 3 живых чтения |
| 14 | `daliHostCapabilities`: неглубокий набор флагов, выставляемых до рендера | «Save to syslog» без syslog и WebSocket-СЕРВЕР Lunatone в браузере только вводят в заблуждение; контроллер — значения по умолчанию | Observable-стор: мутабельность в рантайме здесь не нужна и лишь скрыла бы контракт |
| 15 | Вкладка шлюза: подмена модуля сборкой — единственный шов | Флаг-фолбэк был недостижим в обоих хостах и тянул чужое i18n-пространство в homeui (снят по код-ревью) | Двойной механизм (флаг + подмена) |
| 16 | Двухстрайковый сброс сохранённой установки, с сообщением в журнале загрузки | Первый сбой почти всегда транзиентен (занятый порт, оборванная закачка); установка с именами устройств стоит дорого; сброс объявляется, а не происходит молча | Сброс при первом сбое / вечная блокировка страницы |
| 17 | Память о шлюзах пишется в момент скана + фолбэк из sessionStorage | Очистка профиля браузера оставляла страницу «шлюз не найден» при живом результате скана | Запись только по кнопке (исходное) |
| 18 | Каталог прошивок: sha256 колёс из pyodide-lock, кэш листинга бакета | Байты, попадающие в раздаваемый артефакт, проверяются; сетевой флап деградирует до вчерашнего каталога, а не роняет сборку | Слепое доверие CDN/кэшу |
| 19 | SW: DALI-рантайм кэшируется при первом обращении, не при install | Посетитель Modbus-редактора не платит ~13 МБ за вид, который не открывал | Eager precache (исходное, снято по ревью) |
| 20 | Тесты рантайма — CPython против симулятора; e2e — против sim-режима; vitest — на тулчейне homeui; тесты хеврестик полосы — в homeui, рядом с кодом | Падение — это трейс, а не трейс внутри WASM; тесты живут в том репозитории, чей CI обязан их гонять | Тестировать только через браузер |
| 21 | Пустой ответ `GetGroup` — момент, а не факт: не кэшируется, вкладка говорит «участники инициализируются» и переспрашивает раз в 3 с | Демон сливает параметры только по инициализированным участникам; на холодном старте ответ пуст законно. Кэш пустого ответа замораживал вкладку «только контролы» на всю сессию — воспроизведено на стенде | Показывать пустую форму (исходное) |
| 22 | Спрос о неинициализированном устройстве вытягивает его попытку инициализации вперёд (upstream, wb-mqtt-dali#225) | Первая неудачная попытка уводит устройство в бэкофф до 60 с; страница группы ждала расписание ретраев, а не шину (лог с реального стенда: шина здорова, демон простаивает). Ограничено спрашивающим: один участник поднялся — ответ непуст, страница молчит | Приоритет по умолчанию всем (шум на шине без наблюдателя) |
| 24 | Симулятор и регистровый линк драйвера живут в wb-mqtt-dali; редактор их вендорит | Одна копия, которую гоняет CI демона: новая команда демона ломает тест симулятора там, а не всплывает через месяцы здесь; e2e и отчёты об ошибках демона получают установку без железа (wb-mqtt-dali#226, #227) | Держать копии в редакторе (исходное, ~3 тыс. строк, дрейф) |
| 25 | `TWASMPort::ReadFrame` соблюдает таймауты wb-mqtt-serial и предикат «кадр собран»: ждёт первый байт `responseTimeout`, дальше — пауза `frameTimeout`, отдаёт ответ, как только собран ожидаемый размер; `serial.js` читает чанками с таймаутом вызывающего и не переоткрывает порт на каждую запись | Раньше каждое чтение ждало весь JS-таймаут ответа (250 мс на 115200), а перед каждым `port/Load` wb-mqtt-serial шлёт широковещательный кадр без ответа — итого ~280 мс на любой Modbus-обмен и ~1,4 с на батч из трёх DALI-кадров; замерено на железе: обмен стал ~12 мс, страница устройства открывается за 4 с вместо минут | Терпеть, растянув таймауты драйвера (исходное — маскировало причину и грузило шину) |
| 26 | `RegisterLink` (wb-mqtt-dali#227) считает часы ответа драйвера из измеренной стоимости своих регистровых обменов, а слоты кольца отдаёт по счётчику кадров | Драйвер взводит таймер до начала обмена; на медленном порту бюджет «время шины» истекал раньше собственных операций линка — все кадры «без ответа», хотя они ушли в шину. Слоты по индексу заставляли обработчик видеть «счётчик пошёл назад» и терять 3 кадра из 4 | Специальный таймаут для WASM-хоста в демоне (знание о транспорте не на своём месте) |
| 27 | READY демона не ждёт инициализации устройств: дерево строится из восстановленного конфига, страница наполняется по мере чтения шины | Чтение восстановленной установки с шины — десятки секунд на DALI-скорости (особенно без мемо, ADR 4–5); гейт до 30 с держал весь UI за boot-логом. Посеянные группы стоят до ответа шины, вкладка группы переспрашивает (ADR 21), спрос вытягивает инициализацию вперёд (ADR 22) | Ждать первые инициализации (исходное): «группы верны при первой отрисовке» ценой долгого бута; непосеянное устройство теперь до ответа шины видно без групп |
| 23 | `externalBroker` в `daliHostCapabilities`: без внешнего брокера редактор MQTT-id скрыт | На контроллере id — идентичность устройства для dashboards/rules/history; в loopback-мире он никому не виден. Схема демона его требует — скрывается только редактор, id остаётся дефолтным | Убрать поле из схемы (правка демона) |
| 28 | Тела `EM_ASM` с `Asyncify.handleAsync`: все побочные эффекты только внутри async-колбэка, копирование в буфер — с проверкой длины | Тело исполняется дважды; на unwind-проходе `handleAsync` возвращает значение ПРЕДЫДУЩЕГО `wakeUp`, и `ReadChunk` копировал чужой чанк в более короткий буфер, затирая блок данных Asyncify → `RuntimeError: unreachable` при открытии второго устройства во время загрузки первого (воспроизведено и доказано на стенде 2026-09-02) | Сброс `Asyncify.handleSleepReturnValue` из `serial.js` (оставлен как страховка для старых сборок модуля — зависит от внутреннего имени Emscripten) |

### 9.1. К ADR 3: что ходит по loopback-брокеру помимо RPC

| Топик | Направление / retained | Полезная нагрузка | Производитель → потребитель |
|---|---|---|---|
| `/devices/<id>/meta`, `…/controls/<ctl>/meta`, `…/controls/<ctl>`, `…/controls/<ctl>/meta/error` | демон → UI, retained | JSON-описание устройства/контрола, значение, флаги ошибок `r`/`w` | `DevicePublisher` (`wbmqtt.py`) для каждого gear, DALI-2-устройства, групп `<bus>_group_NN` и `<bus>_broadcast` → `devicesStore` (`/devices/#`) → `DeviceControls`, полоса, readback-слияние |
| те же `…/controls/illuminanceN`, `movementN`, `occupiedN`, кнопки | демон → UI, retained (нажатие потом сбрасывается) | события DALI-2 | `publish_event()` из `_handle_bus_traffic_frame` — спонтанные, без запроса со стороны UI |
| `/devices/<id>/controls/<ctl>/on` | UI → демон, не retained | новое значение | `send-cell-value.ts` → обработчик `+` в `DevicePublisher` → `EXECUTE_CONTROL` |
| `/wb-dali/<bus>/commissioning` | демон → UI, retained JSON | `CommissioningState` `{status, progress, error, device_count, devices, finished_at}`; idle-полезная нагрузка после; снятие пустым payload | RPC `ScanBus` возвращает `progressTopic`, дальше — публикации → `bus-store.subscribeToCommissioning()` |
| `/wb-dali/<bus>/bus_monitor` | демон → UI, QoS 2, не retained | текстовая строка на кадр `hh:mm:ss.mmm << Команда (fc: N)` | `_publish_monitor_line()` → `monitor-store` → `parse-bus-monitor-line` |
| `/wbretainhack/<rnd>` | UI ↔ брокер, QoS 2 | маркер «retained-догон закончился» | `mqtt-client.ts` после connect; демон — зеркальный `retain_hack()` |

Что пришлось бы заменить при отказе от брокера: `/on`, прогресс скана и
retain-hack переезжают на прямые вызовы/колбэки тривиально; плоскость
состояния, события DALI-2 и монитор требуют кэша состояния с уведомлением об
изменениях и начальным снимком для поздно смонтированной вкладки — то есть
retained pub/sub под другим именем. Это и есть граница, по которой брокер
оправдан.

## 10. Качество

Сценарии: (1) открытие страницы устройства ~4 с — порт-слой (ADR 25), без
кэша между сеансами (ADR 4–5 отозваны, SOFT-7409);
(2) сбой шины во время батча деградирует, не роняя коммишининг — `raw_of`,
тест с «мёртвым шлюзом»; (3) обрыв закачки актива не вешает загрузку —
проверка content-length в едином `assetBytes`; (4) всё, чем страница
отличается от контроллера, покрыто пайплайном: pytest 74, vitest 17 (wasm) +
2510 (homeui), e2e 25 (в т.ч. sim-режим и офлайн-сборка с `file://`), полный typecheck/lint homeui.

## 11. Риски и технический долг

- Пятно `fetch-python-sources.sh`: вендоринг по веткам, не по тегам.
  Скрипт теперь штампует точные коммиты (`vendor/.refs`) и перекачивает
  дерево, когда ветка ушла вперёд — переиспользованный workspace CI больше
  не собирает устаревший демон, а штамп говорит, что именно собрано; но
  воспроизводимость относительно upstream-пушей по-прежнему требует тегов.
  Сейчас закреплён за `soft-dali-host-apis` (стек wb-mqtt-dali#226–#228); после
  мержа — обратно на `main`.
- Первые три Modbus-обмена после старта DALI-сервиса занимают ~600 мс каждый
  (переоткрытие порта с `resetUsb` после сканирования); дальше ~12 мс. Не
  мешает, но причина не установлена.
- Каждое открытие страницы устройства платит полную стоимость шины: мемо-кэш
  отозван до появления индикации происхождения данных в UI (код — на ветке
  `soft-dali-memory-cache`). Дизайн возврата — SOFT-7409 и
  `dali-memory-cache-postponed.ru.md`.
- RPC-половина страницы DALI могла бы идти прямыми вызовами обработчиков
  `Gateway` по образцу Modbus-редактора, оставив брокеру только плоскость
  состояния и событий (§9.1). Сегодня — один шов вместо двух; переход
  оправдан, если loopback-брокер начнёт мешать (ADR 3).
- `notes/06` — актуальный список оставшихся UX-наблюдений.
